# 100 图复合巡检异构调度实验设计

## 1. 目标

在 Loom 中构造一个包含多阶段依赖、轻重能力混合和 100 张真实图片的园区巡检任务流，使用 2 个和 3 个受控异构 Slave 分别执行，并对比轮询、最小负载和预计最早完成三种调度策略。

实验必须同时回答三个问题：

1. Loom 能否真实执行 301 个动态节点组成的复合 DAG；
2. Docker 构造的三个 Slave 是否在实际 Loom Attempt 中表现出稳定、可测的性能差异；
3. 感知容量、服务时间和服务状态的调度策略，是否比不感知异构的基线取得更好的任务完成时间和尾延迟。

本实验仍是单机 Docker 受控异构验证，不将结果表述为真实 CPU/GPU/边缘集群结论。

## 2. 研究假设

- **H1：异构有效性。** 对相同输入和相同能力，Slave A、B、C 的实际执行时间分布存在稳定差异，且排序与 CPU 限额和校准画像一致。
- **H2：调度收益。** `earliest_finish_v1` 的整批完成时间和节点 P95 延迟低于 `round_robin_v1`。
- **H3：负载信息收益。** `least_loaded_v1` 优于轮询，但在稳定异构环境中弱于同时使用服务时间的 `earliest_finish_v1`。
- **H4：扩展收益。** 在相同 100 图任务下，A+B+C 拓扑比 A+B 拓扑具有更高吞吐量；扩展收益按策略分别报告，不能只报告最优策略。
- **H5：开销可接受。** 三种策略的平均选点开销都远低于能力执行时间，复杂策略带来的调度开销不会抵消执行收益。

## 3. 现实任务与复合 DAG

任务定义为“园区图片批量巡检”：读取 EdgeFaaSBench 本地归档中的全部 100 张图片，对每张图片完成预处理、目标检测和风险评估，最后生成一份批次报告。

```text
100 张原始图片
      │
      ├─ image.preprocess × 100
      │          │
      │          └─ vision.detect_yolo × 100
      │                         │
      │                         └─ inspection.assess_risk × 100
      │                                             │
      └─────────────────────────────────────────────┘
                                                    ↓
                                      inspection.aggregate × 1
                                                    ↓
                                             最终巡检报告
```

动态节点总数固定为：

```text
100 + 100 + 100 + 1 = 301
```

### 3.1 `image.preprocess`

执行方式为 `container:http/1` 常驻服务。它使用 Pillow 完成：

- Base64 解码和图片合法性检查；
- EXIF 方向归一化；
- 转为 RGB；
- 在不放大图片的前提下限制最长边；
- 重新编码为 JPEG；
- 返回宽、高、输入/输出字节数和 SHA-256；
- 保留 `request_id`、`image_id` 和供 YOLO 使用的 `image_base64`。

该阶段是真实图片处理，不通过人为 `sleep` 制造耗时。

### 3.2 `vision.detect_yolo`

复用并纳入分支管理的 YOLO11n HTTP 服务，执行方式为 `container:http/1`。它读取预处理结果，返回检测框、类别计数和模型推理时间。

### 3.3 `inspection.assess_risk`

执行方式为 `process:json_stdio/1`。它根据 YOLO 检测结果生成单图巡检记录：

- 目标总数；
- 人员、车辆等关注类别计数；
- 最大检测置信度；
- 可解释的风险等级和触发原因。

风险规则必须固定并写入能力包程序，三种调度策略使用同一程序。它不调用大模型，避免随机输出影响性能和正确性比较。

### 3.4 `inspection.aggregate`

执行方式为 `process:json_stdio/1`。它接收 100 个单图巡检结果，生成：

- 成功处理图片数；
- 各风险等级数量；
- 各目标类别总数；
- 高风险图片列表；
- 图片遗漏和重复检查；
- 输入图片 ID 的确定性摘要。

最终结果必须通过 Loom 内容存储返回，实验控制器另将同一内容保存到 benchmark 结果目录，方便人工检查。

## 4. 为什么使用固定 DAG

本实验研究调度，不研究大模型规划。固定 DAG 保证三种策略接收到完全相同的 301 个节点及依赖关系。它只决定“需要执行哪些阶段”，不指定任何节点去哪个 Slave。

Slave 选择仍由 Driver 的 `SchedulingPolicy` 完成。DeepSeek 不进入每轮性能测量，避免规划随机性成为混杂变量。以后研究 Agent 规划时，应使用另一套实验设计。

## 5. 受控异构拓扑

新增 Slave C，并保留 A、B：

| 节点 | 角色 | Slave CPU 上限 | 服务容器 CPU 上限 | 初始有效容量 |
|---|---|---:|---:|---:|
| Slave A | 低性能边缘节点 | 0.50 | 0.40 | 1 |
| Slave B | 普通边缘节点 | 1.50 | 1.00 | 1 |
| Slave C | 高性能节点 | 3.00 | 2.50 | 1 |

初始容量设为 1，因为预处理服务和 YOLO 服务都先使用单 worker 阻塞计算模型。HTTP 可接收请求数不等于有效计算并行度。校准若证明服务实际支持并行计算，才调整容量。

需要支持两种拓扑：

- **2-Slave：** A+B；
- **3-Slave：** A+B+C。

Slave C 需要独立数据库、端口、运行时插件 socket 卷和明确的 `LOOM_SLAVE_ENDPOINT_URL`。不能复用 Slave B 的数据库或状态卷。

## 6. 异构有效性校准

正式对比前必须单独校准，不能只检查 Compose 中写了不同 CPU 数字。

### 6.1 配置证据

记录：

- 三个 Slave 容器的 `HostConfig.NanoCpus`；
- 各能力服务容器的 CPU 限额；
- Observer 中三个 Slave 的活动 lease、运行时支持和调度画像；
- 预处理与 YOLO 能力包在三个 Slave 上的 `ready` 状态；
- 镜像摘要和能力包摘要。

### 6.2 执行证据

对 `image.preprocess` 和 `vision.detect_yolo` 分别执行校准：

1. 使用固定的同一张图片；
2. 通过 `loom.data.locality.v1` 将一个校准 Run 固定到指定 Slave；
3. 每个“能力 × Slave”组合预热 2 次；
4. 再测量 10 次；
5. 从 Attempt 和节点事件读取执行时间；
6. 报告中位数、P95 和变异系数。

只有当至少 YOLO 阶段满足以下条件时，正式策略对比才开始：

- 三个 Slave 均成功完成 10 次测量；
- 中位数满足 `A > B > C`；
- 最慢与最快中位数之比不小于 1.5；
- 每个节点的变异系数不高于 30%。

若不满足，应先调整 CPU 配额或排查宿主机噪声，不能带着无效异构继续实验。

## 7. 每能力调度画像

当前代码只允许每个 Slave 声明一组统一的 `capacity`、`service_time_ms` 和 `cold_start_ms`。这对复合 DAG 不完整，因为图片预处理、YOLO 和风险分析的耗时尺度不同。

调度注册画像扩展为：

```json
{
  "scheduling": {
    "default": {
      "capacity": 1,
      "service_time_ms": 1000,
      "cold_start_ms": 0
    },
    "packages": {
      "image-preprocess-http": {
        "capacity": 1,
        "service_time_ms": 120,
        "cold_start_ms": 500
      },
      "yolo11n-http": {
        "capacity": 1,
        "service_time_ms": 800,
        "cold_start_ms": 1500
      },
      "inspection-assess-risk": {
        "capacity": 1,
        "service_time_ms": 30,
        "cold_start_ms": 0
      }
    }
  }
}
```

Driver 使用 `package.package_id` 选择画像；没有专用条目时使用 `default`。本设计明确要求保留对现有扁平画像的兼容读取，使已有 Compose 和测试不因实验扩展失效。新 Compose 只写新结构。

画像来源仍是 Observer 已接受的 Slave 注册快照，任务输入不能伪造服务时间和容量。

首轮画像来自校准中位数，实验期间固定不变。在线学习画像属于后续研究，不在本次实现中加入。

## 8. 对比策略

### 8.1 `round_robin_v1`

轮流选择可执行且已就绪的 Slave，不使用容量和服务时间。它是“不感知异构”的主基线。

### 8.2 `least_loaded_v1`

使用：

```text
当前在途任务数 / 当前能力的有效容量
```

它感知负载和容量，但不感知不同 Slave 的服务时间，是第二个基线。

### 8.3 `earliest_finish_v1`

使用：

```text
(floor(当前在途任务数 / 当前能力容量) + 1)
× 当前能力预计服务时间
+ 未就绪时的冷启动惩罚
```

它同时感知负载、能力容量、能力服务时间和服务状态，是本实验的目标策略。

三种策略使用完全相同的硬约束筛选；任何策略都不能绕过权限、运行时兼容、Slave 在线状态和数据本地性要求。

## 9. 实验矩阵

### 9.1 开发期检查

| 阶段 | 图片数 | 拓扑 | 策略 | 重复 |
|---|---:|---|---|---:|
| 单元/集成测试 | 合成输入 | 模拟 Slave | 全部 | 自动测试 |
| 冒烟实验 | 3 | A+B+C | 全部 | 各 1 次 |
| 校准实验 | 1 | 单 Slave 固定 | 不比较策略 | 预热 2 + 测量 10 |

### 9.2 正式实验

采用完整的 `2 个拓扑 × 3 个策略` 因子设计：

| 拓扑 | `round_robin_v1` | `least_loaded_v1` | `earliest_finish_v1` |
|---|---|---|---|
| A+B | 100 图 | 100 图 | 100 图 |
| A+B+C | 100 图 | 100 图 | 100 图 |

先进行每格 3 次初步实验。环境稳定后扩大到每格至少 10 次。六种组合按轮次交错执行，每个新轮次随机化六种组合的顺序，并记录实际顺序。

所有失败轮次保留并计入成功率。不能删除异常值后只报告成功样本。

## 10. 控制变量

以下条件在所有正式组合中固定：

- 同一份 100 图 manifest 和 ZIP 摘要；
- 相同图片顺序、请求 ID 和预处理参数；
- 相同能力包摘要和容器镜像摘要；
- 相同 DAG、`max_nodes=301` 和 `max_live_nodes=100`；
- 相同超时、重试和恢复策略；
- 正式实验前所有常驻服务均为 `ready`；
- 相同宿主机 Docker 资源上限；
- 不在正式轮次中运行其他 benchmark；
- 不让 DeepSeek 在不同轮次重新生成 DAG。

策略、拓扑和重复轮次是正式实验中允许变化的变量。

## 11. 指标

### 11.1 正确性指标

- Run 成功率；
- 301 个节点的完成率；
- 输入、预处理、检测和风险结果各为 100 条；
- 图片 ID 无遗漏、无重复；
- 三种策略生成的最终业务报告内容摘要一致。

若业务结果不一致，该轮不能进入纯性能排名，应先判断能力是否非确定或发生数据错误。

### 11.2 性能指标

- 整个 Run 的墙钟完成时间；
- 吞吐量：`100 / Run 完成秒数`；
- 各阶段节点平均值、中位数、P95 和最大延迟；
- DAG 关键路径时间；
- 各 Slave、各能力的分配数量；
- 每种策略的平均和 P95 调度开销；
- YOLO 返回的纯推理时间；
- 各 Slave 的实际服务时间与调度画像之间的相对误差。

### 11.3 扩展性指标

对同一策略计算：

```text
加速比 = T(2-Slave) / T(3-Slave)
扩展效率 = 加速比 / (3 / 2)
```

由于节点不是同构的，扩展效率只作为描述性指标，不能按理想线性扩展直接评价系统好坏。

## 12. 结果目录

```text
benchmarks/results/test_results/composite_heterogeneous_scheduling/
├── calibration/
├── smoke/
├── raw/
└── summaries/

benchmarks/results/task_outputs/composite_heterogeneous_scheduling/
└── <run-id>-inspection-report.json
```

`test_results` 只保存实验配置和指标；`task_outputs` 保存巡检业务结果。每个原始结果必须记录：代码提交、策略、拓扑、Run ID、能力包摘要、镜像摘要、数据摘要和开始时间。

## 13. 实现边界

### 13.1 新增或修改的主要单元

- `capability_services/image_preprocess_http/`：预处理服务源码、Dockerfile、schema、契约和包清单；
- `capability_services/yolo11n_http/`：将本机已有但未纳入分支的 YOLO 服务制品纳入实验分支；
- `loom_v2/settings.py`：解析每能力调度画像；
- `loom_v2/slave/app.py`：注册结构化调度画像；
- `loom_v2/driver/orchestration_runtime.py`：按 package ID 解析候选画像；
- `deploy/docker-compose.heterogeneous.yml`：加入 Slave C 和三节点资源配置；
- `benchmarks/composite_heterogeneous_scheduling/`：能力包注册、校准、Run 构造、执行和汇总程序；
- `tests/`：画像解析、策略选点、301 节点 DAG 和指标采集测试。

### 13.2 不在本次范围内

- DeepSeek 自动生成任务 DAG；
- 在线学习或强化学习调度器；
- 真实 GPU/ARM 设备结论；
- 网络带宽和数据位置优化；
- 与 LangGraph 的 Agent 能力比较。

这些问题不能与本轮调度实验同时引入，否则无法归因收益来源。

## 14. 失败处理与停止条件

- 校准未达到异构有效性阈值：停止正式实验并调整环境；
- 任一能力在任一目标 Slave 上无法激活：停止并修复部署；
- 三种策略的最终业务结果不一致：停止性能比较并排查正确性；
- 301 节点运行触发节点预算、消息大小或超时限制：先修复实验基础设施，再重新开始全部组合；
- 宿主机发生明显后台高负载：该轮标记为无效但保留原始记录和原因；
- 某策略失败：保留失败事实，不通过提高超时或删掉该轮美化结果。

## 15. 验收标准

本阶段完成需要同时满足：

1. 三个 Slave 的配置证据和执行校准都证明异构生效；
2. 100 张图片产生的 301 节点 DAG 至少在一种策略下完整完成；
3. 三种策略在 A+B+C 上均至少完成 3 次正式运行；
4. A+B 与 A+B+C 的扩展对照均有原始结果；
5. 所有策略生成相同的确定性业务摘要；
6. 原始 JSON 能追溯到 Run、Attempt、调度事件、镜像和代码版本；
7. 最终汇报分别陈述结果、限制和未验证内容，不把单机模拟结论扩大到真实异构集群。
