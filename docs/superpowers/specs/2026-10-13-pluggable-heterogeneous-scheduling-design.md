# Loom 可插拔异构调度设计

## 1. 目标

把 Driver 中写死的轮询选点逻辑改造成可配置策略，并用两个受控异构 Slave 证明：在相同任务流下，感知容量与服务启动状态的策略能够降低尾延迟和任务超时率。

本阶段验证的是调度机制，不把同一台 Mac 上的 CPU 限额实验表述为真实 CPU/GPU 异构实验。真实设备复现实验是后续验证。

## 2. 当前问题

`DynamicOrchestrationRuntime._select_target()` 负责权限、兼容性、本地性、激活状态和轮询，筛选规则与选择策略耦合在一起。轮询默认每个 Slave 能力相同，因此在不同容量或不同服务状态下仍平均分配任务。

## 3. 设计

选点分为两层：

1. Driver 保留硬约束筛选：权限、包兼容性、节点在线、本地性要求和排除列表。
2. `SchedulingPolicy` 在合格候选集中做软选择，返回 `SchedulingDecision`。

首批策略：

- `round_robin_v1`：等价于现有行为，作为基线。
- `least_loaded_v1`：优先选择标准化负载最低的节点。
- `earliest_finish_v1`：依据节点声明的并发容量、预计服务时间、当前在途任务以及能力包是否已就绪，选择预计完成时间最早的节点。

预计完成时间采用可解释模型：

```text
预计完成时间 = 排队批次数 × 预计服务时间 + 冷启动惩罚 + 预计服务时间
排队批次数 = floor(当前在途任务数 / 并发容量)
```

Slave 在注册信息的 `capabilities.scheduling` 中声明实验所需静态画像：并发容量、默认服务时间和冷启动惩罚。Driver 只使用 Observer 已信任的 Slave 注册快照，不接受任务输入伪造这些数据。

策略由 `LOOM_SCHEDULING_POLICY` 选择。未知策略应在 Driver 初始化时直接失败，避免静默回退造成实验配置错误。

## 4. 可观测性

每次选择产生结构化证据：策略 ID、候选节点、各节点评分、最终节点和选择原因。证据写入 `node_accepted` / `node_reassigned` 事件，实验程序从 Run 事件和 Attempt 读取结果，不根据 Agent 文本判断执行是否成功。

## 5. 受控异构实验

使用 Compose override 构造两个 Slave：

- `slave-a`：低 CPU 限额、并发容量 1、较长预计服务时间。
- `slave-b`：高 CPU 限额、较短预计服务时间。调度容量必须按能力服务的有效计算并行度填写，不能直接照搬 HTTP 并发上限；当前单进程 YOLO 的有效容量仍为 1。

两种策略使用完全相同的 YOLO 镜像摘要、输入清单、请求到达顺序、并发度、超时和重试配置。至少测试稳定异构、突发负载、冷热状态和节点故障四种场景。

主指标为 P95 端到端延迟与超时率；同时报告成功率、吞吐量、各 Slave 分配数、调度耗时和预测误差。重复运行并报告置信区间。失败策略不能仅凭成功样本延迟参与排名。

## 6. 边界

本阶段不引入复杂学习模型，不自动探测 GPU，也不同时增加多个能力服务。先用 YOLO 将策略接口、证据链和实验闭环跑通，再迁移到真实异构设备并增加图像压缩、视频转码等任务验证泛化性。
