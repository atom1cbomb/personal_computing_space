# Observer 资源目录按需读取

遵循 [spec 设计规范](../spec-design-guidance.md)。本次保持 GRIP 对外行为和 SDK 调用流程，优化 Observer 的目录投影与数据库读取。

## 问题与目标

2026-10-22 生产测量中，SDK 一次 resources() 串行发送六次请求，合计 23.18 秒；各请求耗时 3.50–4.13 秒。Observer 对每次请求都构建全部 531 项目录，生成 Schema 并计算每项描述摘要。构建过程中，查询每个能力包的激活实例又重新加载整个包表；历史 Run 的完整记录也被重复读取。MCUE 过滤在这些工作之后执行。

本次消除这些重复工作。固定资源查询不读取动态目录；动态查询只投影所需资源；列表按 MCUE 选择数据来源并在构建描述前过滤。查询次数不随包数量线性增加。SDK 的六次请求保持不变。

## 读取结构

Observer 初始化时生成工作区、内置 action 和固定 Schema 的条目。它们仅依赖进程配置，可复用至进程结束。DESCRIBE 和 INVOKE 先解析目标条目，输入校验再解析该 action 的输入 Schema；调用其他资源时显式解析依赖，不要求先准备整个目录。

动态目录采用同一个投影函数，接受目标 URI 或 MCUE 过滤。根据资源来源分别读取 MCUE 定义、Slave、包与激活实例、注册资源、Run。单个目标只构建匹配条目；列表保留现有 resource 元数据，只有 DESCRIBE 才计算该条目的 revision。content 直接从 ContentStore 读取。

能力包导出的 action 声明、调用 Schema 和 offer 只由包的不可变内容与 Observer 配置决定，按包 URI 和摘要复用。包的发布状态、激活状态、认证状态、资源属性、Slave 租约和 Run 状态不进入跨请求缓存。每次根据当前发布包集合决定哪些不可变声明可见；包被撤销后，已有缓存不能继续提供该包的导出资源。

## 数据库读取

Repository 增加用于目录的包与激活实例批量读取，一次读取当前工作区的包和对应激活列表，省去事件历史；同时保留现有 Run 存储中符合目录可见性条件的已发布包，只读取包投影，避免加载整个 Run。结果属于本次请求，不写回执行路径的内存状态，也不逐包调用 list_package_activations。

Run 列表只读取当前工作区的 ID 和状态。单个 Run 的 read 只读取其状态和 outcome，cancel 继续走原有执行状态变更流程。资源属性与激活 revision 仍由现有写入路径管理。

MCUE 过滤在投影前决定需要的内置资源族，并先筛选注册资源；注册资源可使用任意已发布 MCUE，不能仅凭类型字符串假定它属于某种存储。只有匹配资源需要绑定能力时才加载相关包与激活信息。动态 Schema 和 action 的直接查询仍检查当前包是否公开可见。

## 一致性与验证

维持现有资源 URI、元数据、offer、revision 算法、鉴权、输入校验、工作区隔离和错误码。激活停止、认证变化、资源属性更新、包发布/撤销和 Run 状态变化在下一次请求可见；多激活绑定仍不能任意选择一个执行实例。SDK 文件不改动。

回归验证包括：固定资源查询零动态目录/数据库扫描；增加包数量后 SQL 查询次数保持常数；过滤查询跳过无关 Run/Slave 等数据源；列表与逐项 DESCRIBE 的资源信息一致；缓存预热后的状态变化、发布与撤销即时可见；数据库实例之间更新后的读取及跨工作区隔离。复用现有 GRIP、MCUE、资源、能力包和认证回归测试。

使用同一份合成数据，在改动前后测量完整 SDK resources()（仍为六次请求）、固定 Schema 读取和 MCUE 过滤查询，报告条目数量、耗时与 SQL 次数。性能测试采用查询次数和数据访问边界作为稳定断言，耗时作为实测证据。本次实现与本地验证完成后记录结果，生产部署另按部署任务执行。
