# SSH 能力包执行限制

## 目标

`vm_ssh_http` 与 `suanli_vm_ssh_http` 使用一致、可发现的执行契约，支持较长脚本、安装和计算任务。遵循 `spec-design-guidance.md`，复用标准库和现有运行时，不引入新的执行协议。

## 执行契约

| 项目 | 新限制 |
|---|---|
| HTTP 请求体 | 8 MiB，按编码后的请求字节数计算 |
| command | 1,048,576 个字符，通过输入 Schema 的 `maxLength` 声明 |
| stdout / stderr | 分别保留前 16 MiB 原始字节；超出设置 `truncated=true` |
| 默认命令超时 | 300 秒 |
| timeout_seconds | 1–3600 秒，超出范围报错，禁止静默缩短 |

两个网关复用一个标准库执行模块。脚本通过 SSH 标准输入交给远端 `sh -s`，不将长脚本塞入命令行参数；需要其他 shell 时脚本显式调用。两个输出管道并行读取，超过保留上限后继续排空，内存不随实际输出量增长。超时杀死本地 SSH 进程组，返回既有 `timed_out`、`exit_code` 字段；SSH 断开不保证远端脱离会话的后台任务终止。

输入 Schema 增加长度和时长限制；`io.v1` 支持标准 `minLength` / `maxLength`，仍由现有 JSON Schema 库验证。重新生成受影响的契约引用。发布版本不可覆盖，两个包升级为 v3，并更新仓库中用于新发布的依赖坐标。

## 调用链

命令最多运行 3600 秒，Slave action 默认预算 3660 秒；运行时业务 HTTP 调用使用该预算，控制请求仍使用原有短超时。进程插件的 invoke 等待跟随 action 预算并额外预留 30 秒，Worker/Observer 转发默认等待 3720 秒。这样 GRIP 仍快速返回 Run URI，执行与读取 Run 分开。

HTTP runtime 与进程插件的响应默认上限均为 256 MiB，覆盖两路 16 MiB 输出经过 JSON 最坏转义及协议封装后的大小；均在流式读取时检查上限。普通控制响应继续使用较小上限。该值是传输上限，命令输出仍由网关按每路 16 MiB 截断。

## 验证

两个网关都验证旧限制以上的脚本、长超时参数、两路大量输出、截断、超时和退出码。用真实本地子进程模拟 SSH，验证脚本通过 stdin 传递以及管道不会堵塞。通过 GRIP 发布和调用真实 HTTP gateway，验证扩展后的输入 Schema、Run 输出和失败语义。验证 runtime 与插件跨越原 4 MiB 响应限制，且业务等待不再被短控制超时截断。运行所有能力包测试及相关运行时、Schema、部署契约检查。
