# Kubernetes 能力包认证探测恢复修复

## 问题与原因

南京 K8s 新实例曾持续显示 `degraded / auth_failed`。代码与本地复现确认：原网关
仅在上一次认证探测成功时安排下一次检查。一次网络错误或超时后，后续健康检查
一直读取已经结束的失败进程，网络恢复也不会再次探测。超时分支还会遗留正在运行
的 kubectl 及凭据插件。

本次确认并修复的是这个无法自动恢复的缺陷。生产连接不可达，未取得首次失败时的
原始诊断，不能据此断言该次生产故障具体由网络、上游服务或凭据刷新中的哪一项触发。

## 修复后的行为

- 成功检查仍每 30 秒复查；网络、超时及未知探测错误按 2、4、8、16、32、60 秒
  退避，之后间隔保持 60 秒。健康检查或服务监督触发到期重试，并发查询共用同一次
  探测。网络恢复后无需重新登录或重启实例即可恢复。
- 普通探测使用现有命令超时配置，默认 30 秒；检查发现超时后终止整个进程组并回收
  子进程。上次成功的后台复查只在这个有界期限内保留认证成功状态。
- 实际设备码提示使用独立的 300 秒等待期限；反复查询不会重启登录进程或延长期限。
  进程退出或等待到期后撤下旧链接，通过同一实例的 `auth-start` 发起新尝试。
- 明确的凭据失效进入 `auth_required`；权限不足、证书和配置错误保持不可自动重试的
  `auth_failed`，修正后可用 `auth-start` 重新检查。
- 服务连接监督将暂时探测失败显示为 `reconnecting`，需要用户登录时才显示
  `pending_auth`。OIDC discovery URL 中的 `openid` 不再使网络超时被误判为登录要求。
- 诊断日志只记录固定原因码和重试间隔，不记录 provider stderr 或凭据。公开认证
  描述仍使用现有统一协议字段。

## 验证

新增回归用例在原实现上先复现失败，再验证修复。测试使用真实本地子进程及其子进程、
可控单调时钟和并发调用，覆盖故障恢复、退避上限、超时清理、设备码过期、不重用旧
链接、权限/配置错误的显式重查，以及诊断日志不泄露凭据。服务流测试覆盖认证恢复后
重新建立转发，外部 Kubernetes 和登录服务使用替身。

```sh
.venv/bin/pytest tests/capability_services \
  tests/slave/test_container_http_runtime.py \
  tests/slave/test_runtime_plugins.py -q
```

结果：**256 passed，48.45 秒**。生成契约 `--check`、Python compileall 和
`git diff --check` 通过。
