# Loom 对外讲稿（精简版）

**日期：** 2026-09-23
**状态：** 对外表述素材
**用途：** 从[竞品对比与 Loom 的特色](competitive-analysis.md)第 4 节抽取，用于对外介绍。面向不了解 Loom 的听众，不假设对方知道能力包、Slave 等内部术语。

## 一句话

> Loom 是面向异构自有资源的联邦式执行底座：把互不相干的机器、云 VM 和外部服务通过能力契约变成可组合的执行面，并让结果可检查、可验收。

## 30 秒版

现在的 agent 框架解决的是「在同一个部署里把 agent 跑起来」。Loom 解决的是另一个问题：你手上已经有一堆互不相同的机器、云主机和外部服务，怎么让 agent 真的用上它们。

我们把每项资源抽象成带输入输出契约的**能力包**，agent 组合这些能力来完成任务。执行过程留下可复查的计划版本和证据，**模型说「做完了」不算完成，以结果和验收为准**。

## 2 分钟版

1. **组合靠契约，不靠代码。** 框架里两个环节要能拼接，必须共享同一份代码和类型；Loom 里两个能力包只要各自的输入输出契约对得上就能组合。所以两个从未设计过要协作的服务——哪怕跨机器、跨技术栈——都能拼在一起。

2. **编排是数据，不是有权限的代码。** 框架的流程图就是执行体，拿到应用的完整权限。Loom 的编排运行在受限沙箱里，只能读内容、发任务、收结果，不能随意访问网络。编排过程因此可以完整留存和复查，执行只认已提交的那一版计划。

3. **先检查就绪，再提交计划。** 因为执行目标不归我们所有，「节点在线」不等于「有空闲资源」，也不等于「这项能力已经认证通过」。所以 Loom 在提交计划前会检查引用、契约和资源状态，能力本身也有待认证到就绪的状态机。

4. **验收是执行路径上的强制状态。** 执行发生在自己控制不到的地方时，退出码 0 和 HTTP 200 更不能代表目标达成。Loom 在能力契约里表达成功语义和验证器，无法自动验证时转人工确认。框架保证「跑到」，观测工具记录「跑过」，Loom 保证「达成」。

5. **缺的能力可以现场造出来，然后复用。** 组合过程中发现缺能力，agent 会在任务内生成候选能力包，验证通过后沉淀为可复用包。发布、安装、认证是三件独立的事，一个包也能先只有接口、没有实现，用来描述资源怎么用。

6. **加新能力不用改核心。** 新增一个普通能力包只需要交付镜像、描述文件和契约，不用动调度和执行的源码；新增一种执行方式由运维安装插件即可。核心只按类型和版本路由，不写业务分支。

## 不要说

- 不要说「我们是一个分布式 agent 框架」——会被直接拿去和 AutoGen、Ray 比规模，而规模不是我们的优势。
- 不要说「支持跨机器执行」——这已经是 agent 框架的标配。
- 要说的三个词是：**异构、契约、验收**。

差异化的战场是让 agent 用上你**已经拥有的、互不相同的**资源，并且证明它真的做到了。
