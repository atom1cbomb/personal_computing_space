## 修复与生产变更

### Outline 正文契约

`documents_info` 和 `documents_documents` 的公开输入改为 `id`。网关兼容旧契约的 `documentId`，拒绝两个标识冲突的输入；动作说明及输出 schema 明确区分正文 `result.data.text` 与子文档目录。上游依据为 [Outline OpenAPI](https://github.com/outline/openapi/blob/main/spec3.yml)。

发布并验证 `outline-http/v4`，包 digest 为 `bf754c254ba3d3871a2803c0e6dc8df5041f386b68bcc5fffa8fb3cdfc4c441d`，镜像为 `localhost:5000/loom/outline-gateway@sha256:ba13619dd2da20026bf03fa6bc41d824eb1703e48a3e6aef6168998d25efb4b1`。新实例实际正文读取成功后才停用旧 v3 实例；旧包和镜像保留用于回滚，未修改业务文档。

### 动态节点并发状态

首个计算 Run `run-a180c00710d7` 的两个分段均 completed、结果摘要正确，但没有归约节点，Run 最终 failed。只读排查发现，Observer 持久化的 `node.execute` 回执同时包含 `node.state=completed` 和 `attempt.state=created`。Driver 因缺少结果引用而终止，不是计算程序算错。

根因是动态节点结果写入没有加入执行事务；它等待内容写入时，队列领取事务从数据库重新装载 Run，替换了内存记录。旧记录写入完成后，响应却读到缓存中的旧 attempt。动态节点接收、派发、重派、完成、失败和相关激活写入现统一进入执行事务，避免这类刷新与写入交错。

新增数据库并发回归：在结果内容写入处暂停，同时执行队列轮询，再核验内存和数据库恢复出的 attempt 均 completed 且带结果引用。测试修复前失败，修复后通过。初次生产更新为 `loom-production-core:node-result-20261028`，保留旧镜像及配置备份。

初版事务修复仍未解决历史扫描开销，扩大事务覆盖也增加了全量读取的机会。后续会话暴露出 Observer 约 96% 单核占用、Driver 心跳反复失效、Run 已领取却不推进：每个事务都复制缓存并读取全部历史 Run，当时 372 个 Run 的 JSON 总量约 20 MB。第二次修复改为在现有事务及数据库锁下按需加载实际访问的 Run、按状态读取执行请求，保留回滚语义。新增回归验证只读取目标 Run、不会解码无关历史，异常后缓存和数据库都回滚。

最终部署 `loom-production-core:node-result-20261028-v2`，两次切换都只更新 Observer，其余 24 个容器未变化。部署后观察到 Observer 瞬时 CPU 约 4%，Driver epoch 稳定；这些是现场观察，不是通用性能基准。第二次计算及首次云 VM 会话已经超时，仍按失败保留；在修复后另开 R9 会话。

### SDK、skill 与凭据边界

SDK 0.9 增加紧凑 `inventory`、`action_contract`、`execute_action`、持久 `CallLedger`、`publish_function`、`submit_map_reduce` 和验证结果摘要的 `wait_run`。map/reduce 构造器派发真实归约节点，并使用 reducer 输出契约；不把客户端计算或编排沙箱临时内容冒充最终远端结果。Volcano 指南修正队列参数语义。

预算账本在调用前检查次数、总文本量和单段长度，失败/不确定调用也计入预算，重试保留幂等身份。但它是 SDK 调用保障：绕过 helper 的直接调用仍可能超预算。本轮论文任务恰好证明，仅新增 helper 和文字说明不足以保证 agent 采用它。

自定义模型服务测试模式改用 root 所有的本地代理注入真实凭据。agent 只获得临时代理入口及占位凭据，不能读取真实 GRIP token 或模型密钥。代理只转发固定上游和公开路径，随容器结束销毁；这隔离了密钥，但没有缩小共享账号的 Workspace 授权范围。兼容的 `auth.json` 模式不具备同样的凭据不可读保证。

## 经验与源码访问的边界

1. 将资源状态、业务执行成功和整项任务验收分开。ready、HTTP 200、CLI 正常退出都不能代替结果核验、预算核对和报告交付。
2. “只凭 skill”应包含经过验证的 SDK 工作流，但 helper 仍可能被忽略。关键预算和权限需在实际调用边界约束，验收应独立从请求和持久结果推导，不能相信 agent 自报 passed。
3. 源码能帮助定位错误，但读取应限制到精确版本和发布者主动公开的文件。此次只读诊断成功，不能据一个样本推断它普遍提高成功率，也不能推断 agent 已能安全自动修复并部署。
4. 读取、修改、发布和切换实例是不同权限。能力包错误应产生最小补丁、回归测试、新不可变版本和独立测试实例，再在授权范围内切换；调用参数错误或登录过期不能成为改包理由。
5. 源码内容摘要和镜像关联可以核验，但关联仍是发布者声明，并非构建来源证明。源码和注释作为证据处理，不作为新的操作指令；不要自动执行下载的源码。
6. 预检通过仅表示部署契约和运行条件满足检查项。新实例不会继承另一个实例的凭据；本机完成认证后，测试机可调用同一个已认证实例，无需复制 Cookie 或从测试机安装登录助手。
7. 用真实数据库及并发轮询复现平台错误。本地内存模式通过不能覆盖缓存替换、数据库持久化和执行回执的一致性。
8. 不向 agent 提供它无须知道的共享密钥。禁止打印的提示词不是隔离；同时审计明文和编码形式，区分凭据不可读与权限最小化。
